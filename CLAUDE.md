# bart.monster

Rust/Axum + PostgreSQL backend and React/Vite frontend. Preserve the original dashboard navigation/components and brown theme. Vercel runs native Rust; Supabase remains PostgreSQL and Google identity. `bart_django` and `bart_django_preview` are historical private schema/role names, not runtime dependencies. Read [README.md](README.md) and [the deployment guide](docs/django-migration.md).

- Use Cargo for Rust and Bun for JavaScript. Run `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --lib`, `bun run --cwd web build`, and `bun run --cwd web test` as appropriate. PostgreSQL tests require explicit local URLs; never use live services for routine tests.
- Keep backend authorization, validation, scoring, and SQL in `rust/src/`. Frontend compatibility modules adapt existing components; they must not become an alternate database client or trust client-supplied scores.
- Ranking writes use `ranking_store` and shared `ranking` rules. Lock users/shared games in deterministic order, validate scoped revisions, and commit rankings plus personal/community daily history in one transaction.
- Every completed tier move autosaves. Serialize requests, retry temporary failures, use server scores/revisions, and protect unsaved navigation. Identical retries acknowledge without writes even if their revision is stale; a different stale payload conflicts. Do not add a manual Save button.
- Enjoyment uses legacy-compatible 10-to-1 normalization independently for board/party and parent-scoped expansions. Difficulty is fixed 1–6: Cuddly, Tame, Challenging, Demanding, Brutal, Monstrous. Same-tier order cannot change difficulty scores.
- `hub_usergame` keeps collection flags, wishlist metadata, ratings/comments, enjoyment, and difficulty independent. Lock the user for personal mutations and prune only wholly empty associations. Ranking does not imply ownership. Difficulty-only rows and inactive wishlist notes/priority survive.
- Retain at most one score per metric/player/game/local day and one community average per metric/game/day. Same-day edits replace today's value, including decreases and null unranking. Earlier days are immutable. No nightly job or intraday events. Use `America/Indiana/Indianapolis` date boundaries.
- Each player's current score counts once. Enjoyment display needs three votes; difficulty needs one and identifies small samples. Store truthful daily averages below presentation thresholds. Never substitute BGG complexity or fabricate votes/history.
- Carry known history through quiet days; show unknown imported periods and null scores as gaps. Never cap all history at a global arbitrary row count. Catalog deletion follows the documented cleanup policy. Account deletion is not exposed by the restored admin UI; any future implementation must remove personal state safely and refresh today's surviving community means for both metrics.
- Cross-mode Unranked is derived eligibility, never a copied vote. Keep revisions/history explicitly metric-scoped. Difficulty votes do not add progression or feed enjoyment predictions.
- Community metric/category filters are independent. Sort players by category-specific enjoyment level, ranked-game count, then stable ID. Keep hot-take red glow always visible; use the largest absolute deviation among games with at least three votes and stable game-ID ties.
- Resolve households from connected partner links consistently and count household games once. Picker tier filters/weights use attending players, including unranked candidates where the mode permits them.
- `auth.rs` handles Supabase PKCE and opaque database sessions. Preserve user UUIDs/permissions; provider metadata never grants staff access. Check active status. Protect every mutation with session-bound `X-CSRF-Token` and exact configured Origin; never trust arbitrary Host headers for redirects.
- `APP_ORIGIN` is explicit in production and can use trusted `VERCEL_URL` in previews. Require secure HttpOnly/SameSite cookies outside localhost. Do not add development login bypasses to deployed builds.
- Chat tools read data only. Preserve conversation/tool bounds, citations, cache invalidation and audit records. Shared expiring `hub_chatlease` rows prevent duplicate paid loops across instances. Never hold database transactions during external/AI requests.
- All runtime SQL must use `crate::db` helpers with `persistent(false)`. Standalone operations must execute through `crate::db::pool(&pool)`, which encloses preparation, binding, result collection and commit in one explicit transaction. Pass existing multi-query transactions directly; never bypass the adapter with a raw pool executor or hold transactions across external requests. Runtime uses Supabase's transaction pooler on 6543 with TLS, one client connection per instance and a five-second idle timeout. Use session pooling on 5432 for explicit migrations. Zero statement-cache capacity and unnamed statements alone do not provide backend affinity; verify the transaction adapter with concurrent live read checks before promotion.
- Keep BGG, Reddit, image and provider fetches bounded. Validate URLs and reject arbitrary redirects. API keys stay server-side. PDF conversion requires staff permission and CSRF. Tests mock paid integrations.
- `cargo run --bin bart-monster -- migrate` is an explicit release step. It applies `0001_application.sql` only when the application schema is empty, then additive Rust SQL. The server never migrates during requests/startup. Verify the private role/search path before release SQL.
- Preserve current production data/backups. Never replay old public migrations or legacy imports over it. Keep old public tables read-only through rollback retention and preserve Supabase Auth.
- Original Next.js source remains at `091d2461f1bf47a6b3b78af7d62275050f33bb20`; Django rollback source at `9a1596e`. Do not claim a pixel-identical brown palette without a recovered reference or a size reduction without a reproducible measurement.
- Leave `ideas.md`, personal email scripts, stories, archive assets and historical Supabase SQL unchanged unless specifically requested. Distinguish local checks, live checks, deployment state and interactive sign-in limitations in documentation.
